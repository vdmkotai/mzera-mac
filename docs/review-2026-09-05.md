# Ревью Mzera for Mac (коммит 99ee140, 5 сентября 2026)

Ревью кода `Sources/`, `Tests/`, `scripts/`, `Package.swift` и документации. Акцент на производительности: задержка ввода, память, фон, энергопотребление. Всё, что помечено «замер», проверено на этой машине (M5 Pro, macOS 26.6.2, Swift 6.3.3) отдельными микробенчмарками; остальное следует из чтения кода.

Проверено перед ревью: `swift build -c release` проходит, `swift test` проходит (20 тестов, 0 ошибок).

Номера строк указаны по коммиту 99ee140. Во время ревью в рабочем дереве шли несохранённые правки `App.swift`, `RenderView.swift`, `ViewerWindow.swift` (клавиши, полноэкранный режим, скрытие панелей). Они сдвигают строки на несколько позиций, но ни одного из перечисленных ниже пунктов не затрагивают.

## Итог

Архитектура выбрана правильно: одна Metal-поверхность вместо NSView на плитку, ограниченные очереди декодирования, SQLite-каталог, zero-copy NV12 через `CVMetalTextureCache`, FramePermit для доставки кадров. Код компактный и в целом аккуратный.

При этом заявленная цель «p95 ≤ 16,7 мс» не достигнута, и в коде есть несколько мест, которые прямо противоречат установке «всё должно быть идеально по перформансу»:

1. Сортировка 100k файлов занимает секунды и запускается при каждом запуске и каждом событии FSEvents. Замер: 3,6 с для 100k в режиме «по папкам / имя»; с предвычисленными ключами 0,27 с.
2. Каждый кадр галереи собирает строковые ключи кэша, мутирует словарь LRU, аллоцирует массивы вершин и переписывает `NSTextField` заголовков. Это лишняя работа на главном потоке именно в момент скролла.
3. Анимированный WebP декодируется квадратично: стоимость кадра растёт линейно с его номером. Замер: кадр 0 — 0,7 мс, кадр 11 — 3,1 мс на 12-кадровом файле.
4. Подготовка текстуры делает две полные копии пикселей (CGContext, затем `replace`). Zero-copy через буферно-backed текстуру в 2–3 раза быстрее и вдвое снижает пиковую память.
5. Переход к следующему фото идёт через `needsDisplay` и цикл CA-транзакций, отсюда 2–3 vsync задержки. Нужен синхронный `draw()` из обработчика клавиши.
6. Таймер 1 Гц постоянно переписывает строки в тулбаре, приложение никогда не «засыпает».

Ниже полный список по приоритетам. P0 — влияет на заявленные цели, P1 — заметно пользователю, P2 — стоит исправить, P3 — мелочи и гигиена.

## P0. Производительность, влияющая на цели проекта

### P0-1. Сортировка: `localizedStandardCompare` и NSString-операции внутри компаратора

`Sources/Mzera/Library.swift:21-36`

Компаратор на каждое сравнение вычисляет `a.folder`, `b.folder`, `a.name`, `b.name` (каждое — `NSString` аллокация) и вызывает `localizedStandardCompare`, самый медленный из доступных компараторов. Для n ≈ 100 000 это ~1,7 млн сравнений.

Замер на 100 000 синтетических путей той же формы:

| Вариант | Время |
|---|---:|
| Текущий код, `.path`, flat | 0,47 с |
| Текущий код, `.name`, grouped | 3,59 с |
| Те же компараторы, но folder/name предвычислены | 2,48 с |
| Предвычисленный натуральный ключ (числа как числа, текст lowercase), `lexicographicallyPrecedes` | 0,27 с |
| Побайтовое сравнение пути | 0,15 с |

Проблема усугубляется тем, когда сортировка запускается (см. P0-2): при каждом запуске, каждом ⌘R и каждом событии FSEvents, даже если ни один файл не изменился.

Рекомендация:
- Один раз построить массив ключей `(folderKey, nameKey, modified, size, index)` и сортировать его, а не `[MediaEntry]`. Натуральный ключ хранить как `[Chunk]` или как сжатую байтовую строку (цифровые группы с префиксом длины), тогда сравнение сводится к `memcmp`.
- Сохранять ключ в `MediaEntry` или в каталоге, чтобы не пересчитывать при повторной сортировке.
- Если нужна именно локаль-зависимая семантика `localizedStandardCompare`, хотя бы предвычислить `folder`/`name` и сравнивать папки только при смене секции (папка одинаковая у длинных серий соседей).
- Добавить тест-бюджет: 100k записей сортируются < 0,5 с.

### P0-2. Полная пересортировка и перезапись 104k строк SQLite при каждом запуске и каждом изменении в папке

`Sources/Mzera/App.swift:307-367` (`startScan`), `App.swift:369-422` (`applyOrder`), `App.swift:635-641` (`rescan`, `folderChanged`), `Catalog.swift:70-98`

Цепочка при обычном запуске: каталог из SQLite показывается быстро (это хорошо), затем стартует фоновый скан, и по его завершении вызывается `applyOrder(restoring: true)` без `alreadySorted`. То есть всегда:

1. полная сортировка (P0-1, секунды CPU);
2. `catalog.save` с `DELETE` + `INSERT` 104k строк и ростом WAL;
3. замена `render.entries` → `sectionsDirty` → O(n) пересборка секций на главном потоке с `NSString`-операцией `folder` на каждую запись (`Library.swift:113-133`).

То же самое происходит после любого события FSEvents (одно изменённое имя файла → полный обход дерева, полная сортировка, полная перезапись каталога) и после ⌘R.

Рекомендация:
- После скана сравнивать результат с `all` (множество `(path, size, modified)`); если совпадает, ничего не делать.
- Если отличается, делать инкрементальное слияние: удалить пропавшие, вставить новые бинарным поиском по уже отсортированному массиву (ключи из P0-1), обновить только затронутые строки SQLite.
- FSEvents отдаёт пути; пересканировать только затронутые директории, а не корень.
- Пересборку секций (`GridLayout.rebuild`) выполнять на очереди сортировки, где отсортированный массив уже есть, и передавать на главный поток готовые `sections`.

### P0-3. Задержка перехода между фото: 2–3 vsync из-за `needsDisplay` и CA-транзакции

`Sources/Mzera/RenderView.swift:93-96`, `RenderView.swift:52-55`, `App.swift:591-609`

Измеренные проектом p50 = 23,8 мс при 120 Гц соответствуют примерно трём кадрам. Путь сейчас: keyDown → `openViewer` → `needsDisplay = true` → возврат в run loop → CA display cycle → `draw(in:)` → `present` на следующем vsync. Сам CPU-кадр 0,2–0,4 мс, то есть всё время уходит на ожидание циклов.

`interact()` выставляет `preferredFramesPerSecond`, но при `isPaused = true` это свойство ничего не делает — код мёртвый и вводит в заблуждение.

Рекомендация:
- В обработчике клавиши/скролла, когда данные уже готовы (текстура в кэше), вызывать `render.draw()` синхронно. `MTKView.draw()` для этого и предназначен при `isPaused = true`. Один кадр ожидания vsync остаётся, два цикла CA уходят.
- Получать `currentDrawable` максимально поздно — после подготовки всех данных кадра, непосредственно перед энкодингом (сейчас порядок уже почти такой, но `nextDrawable` может блокировать при `maximumDrawableCount = 2`, если предыдущий кадр ещё не отобразился; для события ввода это норма, но стоит измерить `presentedTime - scheduledTime`).
- Для видео наоборот: на время воспроизведения переключать view в режим `isPaused = false`, `enableSetNeedsDisplay = false` с `preferredFramesPerSecond`, равным частоте экрана, и показывать последний доставленный кадр. Сейчас каждый видеокадр проходит через CA-транзакцию, отсюда неровная подача (то пропуск, то дубль).
- Убрать `interact()` или заменить на реальную логику.

### P0-4. Анимированный WebP: квадратичное декодирование

`Sources/Mzera/Playback.swift:186-235`

Источник создаётся с `kCGImageSourceShouldCache: false`, а затем кадры запрашиваются через `CGImageSourceCreateThumbnailAtIndex(source, index, ...)`. Для WebP Image I/O не сохраняет состояние между вызовами и собирает кадр `k` из кадров `0..k`.

Замер на `work/fixtures/Section 01/Animated.webp` (12 кадров, 960×540): кадр 0 — 0,73 мс, кадр 5 — 1,8 мс, кадр 11 — 3,1 мс. Для GIF стоимость постоянная (0,6–0,8 мс). Для WebP с 200–300 кадрами последние кадры будут стоить десятки миллисекунд, воспроизведение начнёт замедляться ближе к концу каждого цикла и грузить ядро.

Дополнительно на каждый кадр создаётся новая `MTLTexture` размером до `displayLimit` (при зуме — 8192), то есть постоянная аллокация и освобождение крупных объектов Metal.

Рекомендация:
- Для WebP (и APNG) декодировать последовательно один раз, складывая уже готовые кадры в кольцевой буфер ограниченного объёма (по байтам), или, если анимация целиком укладывается в бюджет, кэшировать все кадры как текстуры.
- Использовать кольцо из трёх текстур (у permit-gate два слота) и `replace` в существующую текстуру вместо `makeTexture` на кадр.
- Ограничить `limit` для анимаций реальным размером кадра, а не `displayLimit`.

### P0-5. Подготовка текстуры: две полные копии и двойная пиковая память

`Sources/Mzera/MediaCache.swift:39-61` (`prepare`), `MediaCache.swift:62-93` (`videoThumbnail`)

Сейчас: Image I/O выдаёт `CGImage` → `CGContext.draw` в новый буфер (копия 1 + конвертация) → `texture.replace` (копия 2). Пиковая память на одно задание = 2 × w × h × 4; для 4096² это 128 МиБ, для 8192² (режим зума) 512 МиБ. Четыре параллельных задания при зуме дают до 2 ГиБ временной памяти, что согласуется с наблюдавшимся пиком 1,5 ГиБ.

Замер (JPEG 4000×3000):

| Размер | CG draw | `replace` | Буферно-backed текстура (один проход) |
|---|---:|---:|---:|
| 2560×1920 | 4,8 мс | 2,3 мс | 1,3 мс |
| 4000×3000 | 10,5 мс | 5,2 мс | 3,2 мс |

Рекомендация:
- Создавать `MTLBuffer` (`storageModeShared`, `bytesPerRow` выровнен на 256), рисовать `CGContext(data: buffer.contents(), ...)` прямо в него и делать `buffer.makeTexture(descriptor:offset:bytesPerRow:)`. Одна копия вместо двух, пиковая память вдвое меньше.
- Добавить быстрый путь: если `CGImage` от Image I/O уже BGRA premultiplied/skipFirst little-endian и sRGB, брать `dataProvider.data` без рисования. В замерах Image I/O отдавал `alphaInfo = noneSkipFirst` с big-endian порядком, так что путь сработает не всегда, но проверка дешёвая.
- Для видеоминиатюр: `sws_scale` умеет масштабировать. Сейчас кадр конвертируется в BGRA в полном размере, оборачивается в `CGContext`, рисуется в RGBA-контекст меньшего размера (`premultipliedLast`, другой порядок байт), потом `prepare` рисует ещё раз в BGRA. Три прохода по пикселям вместо одного: масштабировать в `sws` сразу в целевой размер и BGRA и загружать напрямую.

### P0-6. Работа на главном потоке в каждом кадре галереи

`Sources/Mzera/RenderView.swift:148-259` (`draw`), `RenderView.swift:261-293` (`updateHeaders`), `MediaCache.swift:154-163`, `Library.swift:213-219`

На каждый видимый тайл в каждом кадре:
- `cache.get(entry, limit: 512)` строит строку `"v1|path|size|modified|limit"` (интерполяция с `Double`), хеширует её и **пишет** в словарь LRU (обновление stamp), при промахе ещё `isFailed` строит ключ второй раз;
- `quad()` аллоцирует Swift-массив из 6 вершин на каждый прямоугольник (фон, миниатюра, значок видео, четыре ребра выделения — до 7 аллокаций на тайл) и делает отдельный draw call;
- `updateHeaders()` для каждой видимой секции считает `hasPrefix`/`dropFirst`/`trimmingCharacters`, а затем безусловно присваивает `stringValue` и `frame` каждому `NSTextField`. Присваивание строки инвалидирует текстовый слой: AppKit перерисовывает текст заголовков на каждом кадре скролла в режиме «по папкам».

Для 4K-экрана с плитками 90 pt это сотни тайлов и порядка 2–3 тысяч аллокаций и draw call'ов на кадр. Metal это переживает, но это ровно та лишняя работа, которая отделяет «120 FPS обычно» от «120 FPS всегда».

Рекомендация:
- Ключ кэша сделать `struct Key: Hashable { path: String; size: Int64; modified: Double; limit: Int }` или, лучше, целочисленный id записи + limit. Строку с SHA256 строить только для дискового имени.
- LRU на двусвязном списке с O(1) touch и без записи в словарь при `get` (см. P1-1).
- Собирать все вершины кадра в один `MTLBuffer` (кольцо из 2–3 буферов) и рисовать один `drawPrimitives` на текстуру, а все «белые» прямоугольники (фон, рамки, значки) одним вызовом. Ещё лучше: инстансинг с per-instance данными (rect, uv, color, texture index через argument buffer или texture array).
- В `updateHeaders` сравнивать с прошлым значением и присваивать `stringValue`/`frame` только при изменении. Название секции вычислять один раз при `rebuild`, а не на каждом кадре.
- Вычислять `layout.visible` один раз на кадр и переиспользовать в `refreshRequests` (сейчас три вызова на событие скролла: два в `refreshRequests`, один в `draw`).

### P0-7. Таймер 1 Гц навсегда, обновляющий UI без изменений

`Sources/Mzera/App.swift:107-110`, `App.swift:660-671`

`statsTimer` раз в секунду вызывает `updateStatus()`, который безусловно присваивает `titleField.stringValue` и `status.stringValue` (с `count.formatted()` и интерполяцией). Даже без `--metrics` приложение каждую секунду будит главный поток, инвалидирует два текстовых поля и коммитит CA-транзакцию. Приложение никогда не переходит в состояние покоя, что видно в Activity Monitor как постоянный ненулевой CPU и мешает App Nap.

Рекомендация: таймер включать только при `--metrics`; `updateStatus` вызывать событийно (смена выбора, завершение скана/сортировки) и присваивать строки только при изменении.

## P1. Заметные проблемы производительности

### P1-1. `ByteLRU.trim` — O(n) на каждое вытеснение

`Sources/Mzera/Library.swift:232-237`

`items.min(by:)` проходит весь словарь на каждое вытеснение. Для кэша миниатюр (384 МиБ / ~0,5–1 МиБ ≈ 400–800 записей) каждый `put` при полном кэше стоит O(n); при снижении лимита под memory pressure (384 → 64 МиБ) вытесняется несколько сотен записей подряд, O(n²). В абсолютных числах это единицы миллисекунд, но на главном потоке в момент скролла. Плюс `get` мутирует словарь (см. P0-6).

Рекомендация: классический LRU (словарь + двусвязный список с O(1) touch/evict) или generation-based clock без записи при чтении.

### P1-2. Ключи и `wanted` в `MediaCache.pump`: строки на каждую итерацию

`Sources/Mzera/MediaCache.swift:164-168`, `178-190`, `230`

`pump()` вызывается после каждого завершённого задания и на каждом `request()` (то есть на каждом событии скролла). Внутри для каждого элемента `wanted` (100–200 при overscan 0,5 высоты) строится строковый ключ, а в completion `wanted.contains(where:)` строит ключи ещё раз. При скролле трекпадом (до 120 событий/с) это десятки тысяч строковых интерполяций в секунду на главном потоке.

Рекомендация: хранить ключ в `Request` один раз, держать `wantedKeys: Set<Key>`; `refreshRequests` троттлить до одного раза на кадр (например, вычислять в `draw` или через `CADisplayLink`-тик), а не на каждое событие скролла.

### P1-3. Лимиты параллелизма не соответствуют железу и форматам

`Sources/Mzera/MediaCache.swift:187`, `CMedia.c:39`

Четыре задания на фото и одно на видео на машине с 18 ядрами. AVIF в Image I/O стоит 50–100 мс на миниатюру (замер: 56 мс для 512 px; в `corpus-diagnostic.json` 102 мс). Коллекция содержит 18 086 AVIF: экран из 60 AVIF-миниатюр заполняется ~1,5 с при четырёх потоках. Видеоминиатюры: один поток, программный декодер (`mz_open(path, 0, 0, …)`), плюс `avformat_find_stream_info` на каждый файл. Для 2 360 WebM в фильтре «Видео» это медленное заполнение сетки.

Рекомендация:
- Лимит фото = `min(activeProcessorCount - 2, 8)` с одним зарезервированным слотом под urgent; на E-ядрах (`.utility`) можно держать отдельный пул для overscan.
- Видеоминиатюры: 2 слота и `hardware = 1` для H.264/VP9 (проектом уже подтверждено, что VideoToolbox их берёт); ограничить `probesize`/`analyzeduration` для миниатюр.
- Брать не первый кадр (часто чёрный), а кадр на ~10 % длительности через `mz_seek`.

### P1-4. Дисковый кэш миниатюр: PNG, отдельная транзакция SQLite на каждое касание

`Sources/Mzera/MediaCache.swift:197-207`, `249-271`; `Catalog.swift:99-119`

- PNG-декод 512² ≈ 2–4 мс, PNG-энкод ≈ 10–20 мс. Попадание в дисковый кэш проходит через `fileExists` (лишний stat), `CGImageSource`, PNG-декод, затем P0-5 с двумя копиями. Промах стоит полноценный энкод. Документация признаёт, что формат выбран временно.
- `touchCache` делает `UPDATE` в отдельной autocommit-транзакции на каждое попадание; при скролле это сотни записей в WAL в секунду на очереди каталога, которая одновременно обслуживает `load`/`save`.
- `trimCache` каждые 100 завершений делает `SELECT SUM(bytes)` по всей таблице (полный скан 100k строк) и сортирует по `touched` без индекса.
- Лимит в `pump` захардкожен 30 ГиБ (`MediaCache.swift:241`), тогда как `init` читает `diskCacheGiB` из настроек. Расхождение.

Рекомендация:
- Формат: сырой BGRA (или BGRA + lz4) с `mmap` и `replace`/blit напрямую в текстуру — попадание ≈ 0,1–0,3 мс; либо JPEG q≈0,8 (30–50 КБ на файл, декод ≈ 1 мс аппаратно). При 104k файлов сырой формат даст ~100 ГиБ, поэтому JPEG или сжатые текстуры (ASTC/BC7 через `MTLTextureCompression`) практичнее.
- Касания копить в `[String: Double]` и сбрасывать одной транзакцией раз в несколько секунд; сумму байт хранить в памяти; индекс `cache(touched)`.
- Один источник правды для лимита диска.

### P1-5. Ключ кэша зависит от `limit`, а не от фактического размера декода

`Sources/Mzera/App.swift:239-243`, `MediaCache.swift:154-160`

Одно и то же фото 1200 px запрашивается под ключами 2560, 4096 (после ресайза окна за порог) и 8192 (после зума) — три идентичных декода и три копии в памяти. Кроме того, при зуме `displayLimit = 8192` заставляет перекодировать большие оригиналы в текстуру до 256 МиБ, а при снижении бюджета под memory pressure такой результат отбрасывается и помечается как failed, после чего `showPrepared` показывает «Unsupported or damaged image» (`App.swift:482-483`) для исправного файла.

Рекомендация:
- После декода регистрировать результат под всеми ключами с `limit ≥ max(w, h)` источника (или хранить размеры источника в каталоге и нормализовать `limit` заранее).
- Различать «отклонено по бюджету» и «не декодируется» — разные сообщения и разное поведение (по бюджету можно показать 2560-версию).
- Для зума рассматривать тайловую загрузку (`CGImageSourceCreateThumbnailAtIndex` с большим `limit` не тайловый), либо хотя бы предел 8192 заменить на `min(8192, sourceMax)`.

### P1-6. Программное видео: новый `CVPixelBuffer` с IOSurface на каждый кадр

`Sources/CMedia/CMedia.c:113-135`

Для VP8/MSMPEG4 (есть в коллекции) каждый кадр — `CVPixelBufferCreate` с IOSurface (сотни микросекунд плюс page faults на 8 МБ) и `sws_setColorspaceDetails` заново. Нужен `CVPixelBufferPool` с теми же атрибутами и настройка colorspace только при смене параметров `sws`.

### P1-7. Progressive-скан: копия всего массива на каждый батч

`Sources/Mzera/App.swift:334-341`

`render.entries = self.all` делит буфер с `all`; следующий `self.all.append` вызывает полную копию (memcpy + retain строк на каждую запись). При 104k файлов и батчах по 256 это ~400 копий растущего массива: суммарно сотни мегабайт memcpy и ~20 млн атомарных retain на главном потоке во время первого сканирования.

Рекомендация: хранить в `RenderView` только счётчик/срез или добавлять батч и в `all`, и в `render.entries` (`append(contentsOf:)` без переприсваивания).

### P1-8. Сканер: `FileManager.enumerator` и `Set(keys)` в цикле

`Sources/Mzera/Library.swift:64-88`

2,24 с на 104k файлов при прогретом кэше. `getattrlistbulk` даёт те же атрибуты (тип, размер, mtime) пачками по директории и обычно в 3–5 раз быстрее. `Set(keys)` строится заново на каждый файл. Ещё сканер не пропускает `._*` (AppleDouble на внешних дисках) и скрытые файлы — они попадут в сетку как «битые» плитки.

### P1-9. Миниатюры без mip-уровней

`Sources/Mzera/MediaCache.swift:51-54`, `Shaders.metal`

Текстура 512 px сэмплируется линейным фильтром в плитку 180–320 px без mipmap: минификация в 1,6–2,8 раза даёт алиасинг и мерцание при скролле, а также лишнюю полосу пропускания. Либо генерировать mipmaps (blit encoder после загрузки, +33 % памяти), либо выбирать размер миниатюры по размеру плитки (256/512).

### P1-10. Пауза и ожидание в Playback через опрос

`Sources/Mzera/Playback.swift:109-113`, `142-146`, `195-199`, `225-227`

Пауза — цикл `Thread.sleep(0.01)`, то есть 100 пробуждений в секунду на паузе. Ожидание кадра — sleep-цикл шагом 1–8 мс. Заменить на `NSCondition`/`DispatchSemaphore` с таймаутом до следующего дедлайна. Также при `muted` аудио всё равно декодируется, конвертируется через `swr` и упаковывается в `AVAudioPCMBuffer`, который уходит в `nil`-плеер: пропускать конвертацию, когда движок не запущен.

## P2. Корректность и надёжность

### P2-1. 10-битное видео молча даёт чёрный экран

`Sources/Mzera/RenderView.swift:121-131`

Принимаются только `420YpCbCr8BiPlanar{Video,Full}Range`. VideoToolbox для HEVC Main10, VP9 Profile 2 и AV1 10-bit отдаёт `420YpCbCr10BiPlanar*` (`x420`). `showPixel` возвращается без ошибки, пользователь видит пустой экран и «VideoToolbox frame» в подсказке. Нужно либо запрашивать 8-bit NV12 у декодера, либо добавить путь `r16Unorm`/`rg16Unorm` с делением на 64 в шейдере (и заодно BT.2020 матрицу).

### P2-2. Любая ошибка декодера прерывает воспроизведение

`Sources/CMedia/CMedia.c:149`, `158`, `163`; `Playback.swift:116-136`

`avcodec_receive_frame`/`send_packet` возвращают ошибки на повреждённых пакетах регулярно (особенно AVI и старые кодеки). Сейчас это `-1` → «Cannot decode this video». Нужно пропускать пакет и продолжать, считая подряд идущие ошибки.

### P2-3. Гонка при переключении режима и события FSEvents во время скана

`Sources/Mzera/App.swift:307-313`, `635-641`

`rescan()` до готовности каталога молча игнорируется (`guard rootCatalogReady`). `folderChanged` во время скана выставляет `rescanAfter` — верно, но по завершении всё равно запускает полный скан (P0-2).

### P2-4. `Catalog`: нет проверки кодов возврата

`Sources/Mzera/Catalog.swift` целиком

Ни один `sqlite3_prepare_v2`/`step` не проверяется. Повреждённая БД или `SQLITE_BUSY` (несмотря на busy_timeout) превращаются в тихие no-op: `save` может закоммитить пустой список после успешного `DELETE`, если `INSERT`-prepare упал. Минимум: проверять `prepare` и откатывать транзакцию при ошибке шага; `sqlite3_column_text` может вернуть NULL (`Catalog.swift:132` разыменует без проверки).

### P2-5. Memory pressure снижает лимиты навсегда

`Sources/Mzera/MediaCache.swift:140-148`

После `.warning` лимиты 64/128 МиБ остаются до перезапуска. Подписаться на `.normal` и восстанавливать значения из настроек (можно с задержкой).

### P2-6. Зум не привязан к курсору, панорамирование не ограничено

`Sources/Mzera/RenderView.swift:315-340`

`magnify` меняет масштаб вокруг центра, а не под указателем; `pan` можно утащить картинку за пределы окна без возврата. Для просмотрщика это базовое ожидание пользователя.

### P2-7. Устаревшие завершения при смене корня

`Sources/Mzera/App.swift:266-271`, `MediaCache.swift:169-174`

`openRoot` вызывает `cache.clear()`, но активные задания (до 5) завершаются позже и проверяют только `wanted`. Если новый корень успел запросить тот же файл (пересечение папок), результат корректен; если ключи совпали случайно после `clear` + повторного `request` — тоже. Гонки нет, но `didPrepare` для старого пути может вызвать `showPrepared` нового просмотрщика: он сравнивает `current?.path == path`, поэтому безопасно. Отмечаю как место, требующее теста.

### P2-8. Расширения

`Sources/Mzera/Library.swift:11-15`

Нет `jfif`, `jpe`, `jp2`, `heics`, `mpg/mpeg`, `3gp`, `wmv`, `flv`, `ts`, `ogv`. Для домашней коллекции `jfif` и `mpg` встречаются часто.

## P3. Сборка, упаковка, тесты, документация

### P3-1. 16 динамических библиотек Homebrew в бандле, включая энкодеры и TLS

`scripts/bundle-libraries.py`, `dist/Mzera.app/Contents/Frameworks`

В приложение-просмотрщик попадают `libx264`, `libx265`, `libSvtAv1Enc`, `libmp3lame`, `libssl`, `libcrypto` (33 МиБ). Это лишнее время dyld на запуске (загрузка и проверка подписи 16 образов), лишняя поверхность атаки и жёсткая привязка к ABI конкретной сборки Homebrew (отсюда требование macOS 26). Правильный путь — собственная минимальная статическая сборка FFmpeg: `--disable-everything --enable-demuxer=matroska,webm,mov,avi --enable-decoder=h264,hevc,vp8,vp9,av1,msmpeg4v1,msmpeg4v2,msmpeg4v3,mpeg4,aac,opus,vorbis,mp3,pcm_* --enable-protocol=file --enable-hwaccel=*_videotoolbox --disable-network --disable-programs`, плюс `libdav1d` статически. Один бинарник, старт быстрее, требование к ОС снимается.

### P3-2. `Package.swift`

- `unsafeFlags` с абсолютным путём `/opt/homebrew/opt/ffmpeg`: сборка не воспроизводима на другой машине; после P3-1 уходит само.
- `swiftLanguageModes: [.v5]` отключает проверки конкурентности Swift 6. Код содержит объекты, к которым обращаются с нескольких потоков (`Playback.position/duration`, `MediaCache` из worker-замыканий читает `catalog`, `device`), и сейчас это держится на дисциплине. Стоит хотя бы включить `-strict-concurrency=complete` как предупреждения.
- `resources: [.copy("Shaders.metal")]` и компиляция шейдеров из исходника в dev-режиме — приемлемо, но `Bundle.module.url(...)!` упадёт при запуске из другого места. Можно встроить metallib в оба режима через плагин сборки.

### P3-3. `build-app.sh`

- Иконка генерируется `sips` из PNG 1,9 МБ при каждой сборке; можно закоммитить готовый `.icns`.
- `Info.plist` без `LSApplicationCategoryType`, `NSHumanReadableCopyright`, `NSSupportsSuddenTermination`.
- Нет `-Xlinker -dead_strip` и `-Xswiftc -enforce-exclusivity=unchecked` для release (второе даёт несколько процентов на горячих циклах, но требует уверенности в отсутствии эксклюзивных нарушений).

### P3-4. Тесты

Покрытие для первой версии хорошее (layout, LRU, каталог, отмена, permit). Не хватает:
- бюджетных тестов производительности: сортировка 100k < 0,5 с, `visible()` < 50 мкс, один кадр `draw` без аллокаций в горячем цикле (можно проверить через `measure` с `XCTMemoryMetric`);
- теста квадратичности анимации (время кадра n не должно расти с n);
- теста на 10-bit pixel format в `showPixel`;
- теста, что рескан без изменений не вызывает `catalog.save`;
- `testRapidAnimationCancellation` завязан на тайминги (`asyncAfter` 5 мс шаг) и будет флакать на загруженном CI.

### P3-5. Документация

- `docs/verification.md` ссылается на «свидетельства» в `work/`, который в `.gitignore`. Либо коммитить JSON без имён файлов, либо не ссылаться.
- `README.md` описывает «до четырёх фото и одна видеоминиатюра» как достоинство; после P1-3 обновить.
- В `docs/architecture.md` утверждение «изменение ширины пересчитывает геометрию по готовым секциям» верно, но не упомянуто, что смена `entries` пересобирает секции на главном потоке за O(n) с NSString (P0-2).

### P3-6. Мелочи по коду

- `Sources/Mzera/App.swift:45` `launchTime` не используется.
- `Sources/Mzera/MediaCache.swift:154-157` лишняя переменная `text`.
- `Sources/Mzera/RenderView.swift:176` `labels.forEach { $0.isHidden = true }` на каждом кадре просмотрщика; достаточно при входе в режим.
- `Sources/Mzera/App.swift:405` восстановление выбора через линейный `firstIndex` по 104k строк — один раз на сортировку, допустимо, но с индексом `path → position` из P0-1 будет O(1).
- `Sources/CMedia/CMedia.c:42` `VTRegisterSupplementalVideoDecoderIfAvailable` вызывается при каждом открытии; достаточно одного раза (`dispatch_once`).
- `Sources/Mzera/Playback.swift:11` `AVAudioFormat(...)!` при `standardFormat` безопасно, но `engine.connect` с несовпадающим форматом микшера при смене устройства вывода упадёт молча в `catch` — стоит логировать.
- `Sources/Mzera/Library.swift:39-52` `Cancellation` на `NSLock` опрашивается в горячих циклах; `ManagedAtomic<Bool>` из swift-atomics или `OSAllocatedUnfairLock` дешевле, хотя разница здесь незаметна.
- `Shaders.metal`: сэмплирование `bgra8Unorm` (не `_srgb`) даёт фильтрацию в гамма-пространстве. Для миниатюр с mipmap (P1-9) стоит перейти на `bgra8Unorm_srgb` для текстур и drawable.

## Рекомендуемый порядок работ

1. P0-1 + P0-2 вместе: ключи сортировки, сравнение результата скана с текущим состоянием, инкрементальное слияние. Убирает секунды CPU при каждом запуске.
2. P0-3: синхронный `draw()` на ввод, отдельный режим подачи кадров для видео. Это единственный путь к p95 ≤ 16,7 мс.
3. P0-5 + P1-9: буферно-backed текстуры, mipmaps, нормальный путь видеоминиатюр.
4. P0-6 + P1-1 + P1-2: структурный ключ кэша, O(1) LRU, батчинг вершин, диффинг заголовков, троттлинг `refreshRequests`.
5. P0-4: кэш кадров анимации и кольцо текстур.
6. P0-7, P1-10: убрать таймер и опросы, чтобы приложение действительно простаивало в покое.
7. P1-3, P1-4: параллелизм под железо и новый формат дискового кэша.
8. P2-1, P2-2: 10-bit и устойчивость к битым пакетам.
9. P3-1: статический минимальный FFmpeg.

Тесты производительности из P3-4 стоит добавлять параллельно с пунктами 1–5, чтобы регрессии ловились автоматически.
